# TLS 1.3 四进程性能压测

测量时间：2026-10-24T11:10:13Z。本报告记录实测结果，不将独立引擎计时当成业务端到端延迟。

## 实测结论

在本机共享 2 CPU、3.74 GiB 内存的条件下，TLS 1.3 已能完成真实四进程业务闭环，但仍未达到高并发低尾延迟目标。每秒固定到达 1 个小请求时表现较好；持续高并发会耗尽预热库存，长尾明显。性能取决于后台补库存和跨端交互，不能用独立引擎的 4.7 ms 推导业务 QPS。

- **较低负载：** 1 RPS 的 60 个 JSON 请求全部成功；完整响应 P50/P95/P99 为 249/278/354 ms，其中上游固定等待 200 ms。直连 P95 约 201 ms。
- **请求前确认 READY：** 100 个 JSON 请求全部成功，P50/P95 为 298/341 ms；这是有前置等待的测量，不能视为无等待的持续吞吐。
- **小请求持续吞吐：** 1/4/8 并发的稳态完成速率均约 1.37 请求/秒。4 并发的 JSON 完成 P95 为 11.55 秒；8 并发出现一次 25 秒请求超时。
- **流式：** 4 并发 64 个请求全部成功；首内容 P50/P95 为 703/6,697 ms。首内容之后，每请求最大内容事件间隔的 P95 为 58 ms，上游设定间隔为 20 ms。
- **大 prompt：** 1 MiB / 5 MiB 档位、2 并发 JSON 全部成功，稳态完成速率分别约 1.26/0.91 请求/秒，完整响应 P95 分别为 1.76/2.41 秒。5 MiB 流式首内容 P95 为 2.15 秒。
- **通信延迟：** Provider 数据链路每方向增加 5 ms 的字节流延迟后，小请求 JSON 的稳态速率降至约 0.63 请求/秒，四服务 CPU 约 1.00 核；说明跨端交互等待也会限制吞吐。
- **资源：** 无延迟、持续负载时四服务 CPU 通常约 1.7–1.9 核；本轮四进程采样 RSS 合计峰值约 596 MiB，出现在 5 MiB 流式场景。发压端和合成上游另占资源。
- **过载：** 4 RPS 的 240 次计划到达中，98 次成功、8 次 HTTP 504、134 次因发压端达到 16 个在途上限而未发送。不得把这些未发送请求计为服务成功，也不能只报告成功请求的分位数。

最终完成 15 个场景，1,192 个成功请求中包括 409 个直连对照和 783 个网关请求；783 个网关成功请求对应 783 条落盘回执。另有 9 个 HTTP 504 和 134 次发压端丢弃，均保留在数据里。所有被测子进程正常退出，socket 清理完成。

## 压测发现并修复的问题

空预热池的 `Acquire` 原本在每次重新检查库存时广播 `changed`。多个等待者会在没有任何新会话时反复唤醒彼此，形成 CPU 空转。现在仅在实际取出、淘汰、补充或调整库存时通知等待者。

回归测试 `TestEmptyPoolWaitersDoNotWakeEachOther` 使用阻塞的 warmer 和 8 个等待者：旧实现立即失败，修复后通过，并验证库存补充后所有等待者都能完成。修复后 `go test -race ./...` 和 `go vet ./...` 全部通过。压测只改变此处生产逻辑；TLS 引擎、协议和记账规则未修改。

相同配置的一轮前后对照：

| 场景 | 修复前稳态请求/s | 修复后 | Hub 平均 CPU 核数：前→后 | JSON P95：前→后 |
| --- | ---: | ---: | ---: | ---: |
| 4 并发 | 0.97 | 1.37 | 0.74 → 0.41 | 10.56 → 11.55 秒 |
| 8 并发 | 0.91 | 1.37 | 0.76 → 0.40 | 19.23 → 19.66 秒 |
| 4 RPS 到达 | 1.00 | 1.36 | 0.79 → 0.40 | 20.21 → 21.79 秒 |

4 并发本轮稳态吞吐提高约 41%，但尾延迟没有随之改善。当前 `Acquire` 并不保证 FIFO，后来请求仍可能抢先取得新会话；结合本轮长尾，这应成为下一项重点排查与改进。没有做逐阶段 tracing，所以不将所有长尾都归因于这一点。

修复前完整记录见 [基线报告](e2e-2026-10-24-before.md)。上述改善来自各一轮运行，不是统计显著性或所有负载下的提速保证。

## 后续优化优先级

1. 为预热池建立公平、有界的等待队列，明确过载拒绝策略，避免新请求反复抢占旧等待者；继续观测尾延迟。
2. 对预热、Go 转发、TLS/MPC 交互做分阶段 CPU 和延迟 profile。加大 ready 库存只能吸收突发，无法替代持续补库存吞吐。
3. 在实际 Hub/Provider 分机环境验证 RTT、带宽和丢包影响，并延长持续压测；本机两个角色共享 2 CPU，不能按这些数字直接推算独立部署容量。

## 环境和方法

- CPU：AMD EPYC 7R32，进程可使用 2 个逻辑 CPU；内存 3.74 GiB。共享开发主机，未隔离其他系统负载。
- 被测服务为 release Rust Hub/Provider sidecar、Go Hub、Go Provider Agent 四个真实进程；SDK 发压端与 HTTPS 上游也在同一主机。
- 上游使用临时 CA 和虚构凭证，TLS 1.3 / P-256 / AES-128-GCM。真实 MPC、双向 mTLS、Provider 本地投递 ACK、鉴权、规范化、回执和账本 fsync 全部开启。
- 上游收到完整请求后固定等待 200 ms。JSON 返回约 2.5 KiB 文本；SSE 输出 40 个内容事件，间隔 20 ms，随后输出 usage 和 DONE。用量是固定测试值，不代表真实模型分词或推理。
- 发压使用公开 Go SDK 和复用 HTTP/1.1 连接。每个逻辑请求使用唯一幂等键，不主动重试。SDK、上传、排队、加密、响应校验及结算开销均在请求计时内。
- 大 prompt 场景的上游仍固定等待 200 ms，不模拟随 token 数增长的真实模型 prefill；这些端到端数字不能代替实际长上下文模型延迟。
- 主配置：target_ready=2、max_ready=4、单 key/全局预热并发=2、max_leased=16、data_tunnels=16。测试账号限流调整为 100 RPS / 32 并发，避免默认 2 RPS 限流掩盖服务容量。
- 服务请求超时 25 秒，SDK 超时 30 秒。错误请求保留在原始数据中；延迟分位数仅统计成功请求，必须结合错误/丢弃计数解读。
- 同一容量的场景依次运行并保留预热池/自动扩容状态；切换容量或加入延迟时重启部署。每个场景只有一轮，前后对比不构成统计显著性结论。
- 固定并发是闭环：完成后再发下一请求。rate 场景固定到达速率，最多 16 个在途；满额到达记作 dropped，不将其隐藏或算成功。
- ready-json-c1 每次先轮询 readyz，再单独计时请求；检查和等待不计入单请求延迟，但计入整轮耗时。readyz 为瞬时快照，不等于拿到排他的会话租约。其他场景仅在启动前检查一次 readiness。
- delay5 场景仅在 Provider→Hub 数据连接上加入每方向 5 ms 的流水字节流延迟。它不是公网测试，也不模拟带宽限制、丢包、重传或 TCP 拥塞窗口。
- 每 250 ms 读取四个服务进程的 /proc CPU 与 RSS。RSS 相加可能重复计入共享页，不是 PSS；采样峰值不是精确瞬时内存峰值。发压端、上游和延迟代理不计入四服务 CPU/RSS，但在原始资源采样中保留。

## 结论适用范围

这比独立加密微基准更接近实际业务路径，但仍是同机合成上游。分位数使用 nearest-rank；每场景样本数有限，P99 常接近最大值，不应视为稳定 SLO。未测多 Provider 横向扩展、真实模型推理、跨公网丢包、长时间运行泄漏或故障恢复。
