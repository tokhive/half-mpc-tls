# TLS 1.3 四进程性能压测

测量时间：2026-10-26T05:52:56Z。本报告记录实测结果，不将独立引擎计时当成业务端到端延迟。

## 本轮结论与对照

本轮实现了每个会话池独立的 FIFO、有界等待和明确的过载错误，并修复预热线程可能漏掉库存变化通知的竞态。持续并发下长尾明显缩短，持续吞吐没有实质提高。公平性以进入池队列的顺序为准，不保证跨池或响应完成顺序。

完成 15 个场景：网关成功 775 次，对应 775 条落盘回执；另有 14 次队列超时和 130 次发压端满额未发送。所有直连对照成功，全部被测进程正常退出、socket 清理完成。

与 2026-10-24 修复 CPU 空转后的基线相比，CPU 配额、上游延迟、容量、预热并发、发压时长等保持一致。Provider Agent 和 Rust sidecar 二进制 SHA-256 相同，仅 Go Hub 二进制变化。新版本另外启用了 64 个等待者 / 10 秒等待上限，旧版本没有单独的队列上限；过载场景的延迟必须结合拒绝数量比较。各一轮运行，且不是同一时刻的配对实验，不代表统计显著性结论。

## 实现与验证

- 使用每个池独立的链表等待队列及队首通知，避免新请求插队和等待者同时争抢；取消、超时、注销或关闭会移除等待者。注销后重新注册同一 key，不迁移旧等待者。
- 预热线程在检查库存的同一临界区取得通知 channel，避免检查后、订阅前的库存变化丢失。FIFO 和该修复同时进入本轮，没有单独拆分两者的性能贡献。
- Hub JSON 支持 max_waiters / queue_wait_timeout_ms，Go 嵌入配置支持 MaxWaiters / QueueWaitTimeoutMS。0 使用 64 / 10000 ms 默认值，负值拒绝；更早的总请求或调用方 deadline 优先。队列等待上限不截断已取得会话后的推理或 SSE。
- HTTP 503 使用 queue_full / queue_timeout，携带 Retry-After。SDK 现有 APIError 可直接识别。拒绝发生在向上游写入之前，会取消余额预留，不惩罚 Provider 健康分。原幂等键仍绑定失败任务，重试策略见业务接入文档。
- 路由和 readiness 扣除等待者已占据的库存需求；池统计增加 Waiting、MaxWaiters、AcquireRejected、AcquireTimedOut。
- 回归覆盖 FIFO、队首/中间取消、新请求加入、队列上限、等待超时、后继请求继续取得库存、关闭、父 context 取消、注销重注册、补库存通知竞态、503 错误映射及余额退款。go test -race ./...、go vet ./... 通过，默认 TLS 1.2 四进程 JSON/SSE/SDK 冒烟通过。

## 显式过载配置验证

另用 max_waiters=4、queue_wait_timeout_ms=1500，在相同真实四进程链路施加 4 RPS、60 秒负载：77 成功，163 拒绝，0 次发压端丢弃。上游收到 77 个请求，落盘回执 77 条。错误分类为 {"TokenHive HTTP 503 (queue_full): Provider wait queue is full": 88, "TokenHive HTTP 503 (queue_timeout): Provider queue wait timed out": 75}。

这轮用于验证满队列和限时退出，不与默认配置的成功延迟作吞吐提升比较。已核对持久账本：cancel 数量与拒绝数一致，所有取消任务均未产生 settle 回执；所有成功样本的任务 ID 与 settle 记录集合完全一致。详见 [过载验证报告](e2e-2026-10-26-overload.md) 和对应 JSON。

```sh
python3 scripts/benchmark-e2e.py --seconds 45
python3 scripts/benchmark-e2e.py --seconds 45 --only json-rate4 --max-waiters 4 --queue-wait-timeout-ms 1500
```

下一瓶颈仍是持续预热吞吐和跨端交互。当前没有新增分阶段 CPU profile，也没有扩大 CPU 或分机测量；不能将这些结果外推为真实公网或生产模型容量保证。

## 环境和方法

- CPU：AMD EPYC 7R32，进程可使用 2 个逻辑 CPU；内存 3.74 GiB。共享开发主机，未隔离其他系统负载。
- 被测服务为 release Rust Hub/Provider sidecar、Go Hub、Go Provider Agent 四个真实进程；SDK 发压端与 HTTPS 上游也在同一主机。
- 上游使用临时 CA 和虚构凭证，TLS 1.3 / P-256 / AES-128-GCM。真实 MPC、双向 mTLS、Provider 本地投递 ACK、鉴权、规范化、回执和账本 fsync 全部开启。
- 上游收到完整请求后固定等待 200 ms。JSON 返回约 2.5 KiB 文本；SSE 输出 40 个内容事件，间隔 20 ms，随后输出 usage 和 DONE。用量是固定测试值，不代表真实模型分词或推理。
- 发压使用公开 Go SDK 和复用 HTTP/1.1 连接。每个逻辑请求使用唯一幂等键，不主动重试。SDK、上传、排队、加密、响应校验及结算开销均在请求计时内。
- 大 prompt 场景的上游仍固定等待 200 ms，不模拟随 token 数增长的真实模型 prefill；这些端到端数字不能代替实际长上下文模型延迟。
- 主配置：target_ready=2、max_ready=4、单 key/全局预热并发=2、max_leased=16、data_tunnels=16。测试账号限流调整为 100 RPS / 32 并发，避免默认 2 RPS 限流掩盖服务容量。
- 队列配置：max_waiters=64、queue_wait_timeout_ms=10000；FIFO 版本的队列超时独立于请求执行超时。
- 服务请求超时 25 秒，SDK 超时 30 秒。错误请求保留在原始数据中；延迟分位数仅统计成功请求，必须结合错误/丢弃计数解读。
- 同一容量的场景依次运行并保留预热池/自动扩容状态；切换容量或加入延迟时重启部署。每个场景只有一轮，前后对比不构成统计显著性结论。
- 固定并发是闭环：完成后再发下一请求。rate 场景固定到达速率，最多 16 个在途；满额到达记作 dropped，不将其隐藏或算成功。
- ready-json-c1 每次先轮询 readyz，再单独计时请求；检查和等待不计入单请求延迟，但计入整轮耗时。readyz 为瞬时快照，不等于拿到排他的会话租约。其他场景仅在启动前检查一次 readiness。
- delay5 场景仅在 Provider→Hub 数据连接上加入每方向 5 ms 的流水字节流延迟。它不是公网测试，也不模拟带宽限制、丢包、重传或 TCP 拥塞窗口。
- 每 250 ms 读取四个服务进程的 /proc CPU 与 RSS。RSS 相加可能重复计入共享页，不是 PSS；采样峰值不是精确瞬时内存峰值。发压端、上游和延迟代理不计入四服务 CPU/RSS，但在原始资源采样中保留。

## 结论适用范围

这比独立加密微基准更接近实际业务路径，但仍是同机合成上游。分位数使用 nearest-rank；每场景样本数有限，P99 常接近最大值，不应视为稳定 SLO。未测多 Provider 横向扩展、真实模型推理、跨公网丢包、长时间运行泄漏或故障恢复。
